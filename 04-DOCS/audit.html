A beautiful shell around a system that cannot run.

The GEOTECH HR Portal is a high-fidelity UI prototype with a competent, unconnected Postgres schema bolted to the side. The React app makes zero database calls. No login can succeed. No request can be submitted. The repository has no entry point and cannot be built into a running site. Judged as an HR system rather than as a demo, seven expert lenses put it at an average maturity of 1.1 out of 5.

01

What this actually is

A Figma Make export, three overlapping copies of the same source, and a database nobody talks to.

The package is a Figma Make export — package.json still names it @figma/my-make-file. It contains a single 4,632-line App.tsx holding the entire product: design system, application shell, routing, and all nineteen screens. Alongside it sits a genuinely well-written five-migration Supabase schema with row-level security on every table.

The two never meet. grep -c supabase src/app/App.tsx returns 0. The only PostgREST call in the whole codebase is one profiles SELECT in src/lib/auth.ts:50. Every employee, request, notification and leave type lives in sessionStorage — per browser tab, destroyed when the tab closes.

The split brain

Authentication reaches a real server. Everything else never leaves the browser tab.

  • supabase.auth.signInWithPassword
  • profiles  (SELECT, one row)
No bridge
Server side — never touched
  • requests

  • audit_logs
sessionStorage["hr_portal_store_v2"]  →  requests · notifications · employees · leaveTypes · nextSeq · nextEmpSeq · nextLeaveTypeSeq

The identity used on the left and the identity used on the right are different key spaces. auth.ts returns session.user.id as the profiles UUID. store.ts keys every employee, manager relationship and request by the string "EMP-00002". All eighteen lookup sites in App.tsx compare one against the other.

The correct join key, session.user.employeeNumber, exists on the session object and is never used as a lookup anywhere in the application.

03

Why nothing works

Seven independent failures, any one of which alone would stop the product.

  1. No login is possible. grep "INSERT INTO auth" supabase/migrations/ returns nothing. No auth.users row is ever created by any migration, so signIn authenticates EMP-00001@hr.company.internal against a GoTrue instance that has no such user.
  2. Even provisioned users cannot match. The eight seeded profiles carry hand-written UUIDs (a0000000-…-000000000001) that can never equal a real auth.uid(). The profile lookup returns null, and the user is shown "Your account is inactive. Please contact HR" — the wrong error entirely.
  3. Identity spaces do not intersect. With a hand-fixed login, getManagerForEmployee(employees, <uuid>) returns null for everyone. Every employee attempting a request is met with "No active manager assigned. Contact HR." No request can ever be created.
  4. My Team is permanently empty. getTeamForManager(employees, session.user.id) filters managerId === <uuid> against "EMP-00002" values. Always zero rows, for every manager.
  5. The session never survives a refresh. subscribeToAuthChanges is exported and has zero callers, so ensureAuthListener() never runs. Every page refresh or deep link logs the user out, while a live JWT keeps auto-refreshing in localStorage.
  6. HR account operations are placebos. createHRUserCredential and updateHRUserCredential are documented empty functions. HR creates an employee, sees "Employee created successfully" — and that person can never log in. Deactivation revokes nothing.
  7. The repository cannot be run or deployed. There is no index.html, no createRoot call, and vite.config.ts is configured as a library build. src/index.ts exports AppShell but not App. The only npm script is build.
04

Verified defect register

Every item below was read in source and confirmed against surrounding context. Location is file and line.

Security

CriticalAny employee can read any other employee's request
src/app/App.tsx:2433 — EmployeeRequestDetailPage

The page does requests.find(r => r.id === id) and renders it with no ownership check. The manager equivalent at line 3241 correctly redirects on request.managerId !== session.user.id; the employee page is simply missing the matching guard. Navigating to /employee/requests/<any-id> exposes the free-text reason field — which for Sick and Maternity Leave is special-category health data under Egypt's PDPL 151/2020 and Article 9 GDPR.

CriticalAll authorization is client-side; every mutation is an unauthenticated local write
src/app/App.tsx — ProtectedRoute:1732, RoleRoute:1738; store.ts:162 saveStore

Role gating, team scoping, request ownership and approve/reject are React state comparisons in JavaScript the user controls, evaluated against a dataset in the user's own sessionStorage. The RLS policies guard nothing the UI actually reads.

CriticalPlaintext credentials for all eight accounts, including the HR administrator
src_extracted/lib/auth.ts:37-44  and  src.zip → lib/auth.ts

The pre-Supabase auth module ships in two places with a hard-coded user table. The field is named passwordHash but stores the plaintext value. Inside src.zip it is invisible to line-oriented secret scanners. Values are not reproduced here; rotate all eight and delete both copies.

HighLogout leaks the previous user's data to the next user in the same tab
src/app/App.tsx:1490 — AuthProvider.logout

logout clears the session but never purges hr_portal_store_v2. On a shared workstation the next person to sign in inherits the previous user's requests, notifications and the full employee directory.

HighNo rate limiting over a perfectly enumerable identity space
src/lib/auth.ts:130 — signIn

Employee IDs are sequential EMP-NNNNN. There is no lockout, no CAPTCHA, no failed-attempt auditing, and no MFA. session.expiresAt is computed at auth.ts:83 and read nowhere.

HighThe whole employee roster ships in the JavaScript bundle
src/lib/store.ts:57-64 — DEFAULT_EMPLOYEES

Names, work emails, personal Egyptian mobile numbers, positions and the complete reporting chain are static module data, readable by anyone who can fetch the bundle.

Database and RLS

CriticalNotifications and audit logs are structurally unwritable by the workflow
supabase/migrations/20260901122725_hr_portal_phase1_1_corrections.sql

Phase 1.1 narrowed both INSERT policies to WITH CHECK (is_hr()) and deferred writes to triggers "added in the security-hardening phase". Those triggers were never written — grep "CREATE TRIGGER" across all migrations returns exactly two, both update_updated_at. An employee therefore cannot notify their manager on submit, and a manager cannot notify the employee on decision. audit_logs will hold zero rows forever.

CriticalAn employee can insert a pre-approved request naming themselves as approver
migrations/…122036_hr_portal_rls_and_seed.sql — requests_insert

The policy is WITH CHECK (employee_id = auth.uid() OR is_hr()). Nothing constrains manager_id, and nothing constrains status. A direct PostgREST call can create a request with status = 'APPROVED' and manager_id set to the employee's own id.

Highis_hr() has EXECUTE revoked from every role, with no compensating GRANT
…122108_fix_security_warnings.sql  +  …122123_revoke_public_execute.sql

The first migration revokes EXECUTE from anon, authenticated; the second revokes it from PUBLIC. Its own header states it "re-grants only to the authenticated role" — that GRANT does not exist in the file, and grep "^GRANT" supabase/migrations/*.sql returns nothing. Policy expressions are evaluated as the querying user, so every policy calling is_hr() — which is every table — is at risk of failing with permission denied for function. This needs a live check against the deployed database before anything else in the SQL layer is trusted.

HighThe approving manager can silently rewrite the request before approving it
…122725_phase1_1_corrections.sql — requests_update

The header claims "only status, decided_at and decision_comment may be modified by the assigned manager." The policy actually locks four columns and leaves roughly fifteen writable — including start_date, end_date and leave_type_name. A manager can convert paid annual leave into unpaid leave with no trace. The OR is_hr() branch is entirely unconstrained.

HighNo decided_by column, and no updated_at on requests
…122001_hr_portal_schema.sql — requests

The schema records when a decision happened but not who made it. HR Request Details is specified to show "Last updated date", which does not exist. decided_at is stamped from the client's own browser clock.

HighThe hierarchy has no self-reference check and no cycle prevention
…122001_hr_portal_schema.sql — profiles.manager_id

The FK exists but nothing stops manager_id = id, and nothing stops a two-person loop. HR can create one in two clicks in the UI. Any future recursive org-chart query would hang.

HighAn employee cannot read their own manager's profile
…122036_rls_and_seed.sql — profiles_select

USING (id = auth.uid() OR manager_id = auth.uid() OR is_hr()) lets a manager read reports, but a report cannot read upward. The "Direct Manager" display that every spec requires is unreadable under the policy as written.

MediumDeleting an auth user with requests fails hard
profiles → auth.users ON DELETE CASCADE vs requests → profiles ON DELETE RESTRICT

The two constraints collide. HR holds a requests_delete_hr hard delete over the whole record set, which is itself unlogged.

Correctness — visible in the running UI

HighEvery date on the three HR screens renders the literal text "Invalid Date"
src/app/App.tsx:1847 fmtDate — called at 3588, 4085, 4133, 4134

fmtDate does dateStr.split("-").map(Number), expecting YYYY-MM-DD. It is passed submittedAt and decidedAt, which are ISO timestamps. "2026-09-02T13:45:12Z".split("-") yields a third element of "02T13:45:12Z", which becomes NaN. The HR Dashboard, the HR All Requests table and HR Request Details all print Invalid Date — the first thing an HR user sees.

CriticalThe Try Again button on My Team does not exist, and the error copy never renders
ErrorState defined at App.tsx:1060 — called at App.tsx:2893

ErrorState accepts {message, onRetry, className}. ManagerTeamPage passes {title, description, action}. All three are dropped: the component falls back to its generic default message and, because onRetry is undefined, renders no button at all. TypeScript would have caught this; no typechecker is installed.

HighA botched icon codemod put the Chrome logo in the sidebar
src/app/App.tsx:52 — lucide-react import

An automated rename to lucide's newer names got three wrong. Chrome as Home means the Dashboard nav icon for all three roles (lines 1228, 1233, 1239) is the Google Chrome logo. Circle as XCircle means the Rejected indicator at line 2704 is a blank circle instead of an ✗. MoveVertical as MoreVertical replaces the overflow menu with up/down arrows. The correct targets were House, CircleX and EllipsisVertical. The uncorrupted import survives only inside src.zip.

HighRequest numbers are minted from a stale closure and collide
src/app/App.tsx:1569, 1597 — createLeaveRequest / createMissionRequest

requestNumber is computed from store.nextSeq read out of the render closure, while the counter is incremented correctly inside the updater. Two rapid submissions, or two tabs, both mint REQ-00001. The same pattern affects EMP- and lt- ids.

HighA throw during submit locks the form at "Submitting…" forever
src/app/App.tsx — LeaveRequestPage:2145, MissionRequestPage:2282

There is no try/catch around the submit path and no errorElement on the router, so any render exception surfaces React Router's default screen with the raw message and a stack trace.

HighHR "Initial Password" is a visible plaintext field that goes nowhere
src/app/App.tsx:3654

Rendered as type="text", so it is shoulder-surfable, and it is passed to createHRUserCredential — an empty function. The password is neither stored nor used.

HighDemoting or deactivating a manager silently strands their whole team
src/app/App.tsx:1673 — updateEmployee

Direct reports keep pointing at a manager who can no longer approve. Their pending requests freeze permanently, and nothing warns HR. The spec explicitly required surfacing this conflict rather than breaking relationships silently.

MediumA TypeScript duplicate-identifier error ships in the source
src/app/App.tsx:66 vs the store.ts import at line 20

UserRole is both imported from store.ts and re-declared locally — TS2440. It ships because there is no typechecker: tsconfig.types.json is dead config and @types/react is not installed.

Accessibility, responsiveness and brand

HighRequest details are unreachable by keyboard or screen reader
src/app/App.tsx:1108 — Table

<tr onClick> is the only route into a request. Across all 4,632 lines there are zero occurrences of onKeyDown, Escape, aria-live, role="status" or focus(). The Modal has no focus trap, no initial focus, no focus restoration and no ESC handling. Textarea, Select and DatePicker set aria-invalid but never link their error text, so validation messages are never announced.

HighThe date pickers open off-screen on a phone
src/app/App.tsx:2236, 2358, 2372

Date and time pairs use grid grid-cols-2 gap-4 with no responsive prefix. At 375 px that yields 131.5 px columns, into which a fixed 272 px CalendarPopover anchored left-0 opens 92 px off-screen on the End Date field. For a firm whose surveyors file mission requests from site, this is the primary device.

HighNo Arabic, no RTL, and the wrong working week
src/styles/fonts.css, theme.css; App.tsx:537 DAY_NAMES

dir= and lang= appear zero times. The loaded Inter subset carries no Arabic glyphs. The calendar is hard-coded Monday-first, which is the wrong week shape for Egypt — where the weekend is Friday and Saturday — even in English.

MediumThe brand is not GEOTECH's brand
src/styles/theme.css, fonts.css

All five specs mandate Graphik typography. The app loads Inter from Google Fonts. The primary colour is a generic corporate blue #1d4e89, not GEOTECH's gold and graphite. A complete dark theme is defined in theme.css and is structurally unreachable, because every surface is hard-coded bg-white.

The world-class HR verdict

Seven expert lenses, judged against a real HRIS rather than against "is this a decent prototype".

HR operations & policy1.5 — a request router, not leave administration
Compliance & labour law1.0 — would not survive a Ministry of Manpower inspection
HRIS data architecture1.0 — one flat table playing five separate roles
Security & data privacy1.0 — the shape of security, almost none of the substance
Employee experience1.5 — coherent shell, no leave balance anywhere
Analytics & reporting1.0 — no reporting surface, no export, no aggregation
Production engineering1.0 — cannot run, serve or deploy as shipped

What an HR system needs that this does not have

These are not missing features. They are missing concepts — nothing in the schema or the client can express them, and every day the system runs it destroys the history that would be needed to add them retroactively.

Leave balancesNo entitlement, accrual, carry-over or quota. An employee can request 60 days and nothing objects. Grep returns zero hits for balance, entitle, accrual.
A working calendarNo holiday table, no weekend definition. end_date − start_date counts Friday and Saturday as leave in a country where they are the weekend.
CancellationNo path out of PENDING except a manager decision, and no way to cancel approved future leave. Because overlap validation blocks any date touching a PENDING or APPROVED request, a cancelled trip poisons those dates permanently.
Delegation and escalationApproval is a single hop to manager_id. When Jordan Lee takes his own leave or resigns, four people cannot submit and their pending requests freeze with no administrative escape.
Statutory leave handlingMaternity Leave sits in the same unfiltered dropdown, routed to a line manager with a Reject button. A statutory entitlement is not a discretionary approval.
AttachmentsNo file storage anywhere. Sick leave beyond a threshold requires a medical certificate in essentially every jurisdiction; there is nowhere to put one.
Effective-dated historyupdateEmployee is {...e, ...data} — a destructive overwrite. Point-in-time headcount, the org chart as of last 31 December, and department composition on the date of an absence are gone forever.
Employment lifecycleNo hire date, termination date, contract type, probation or rehire. Egyptian Labour Law 12/2003's 21→30 day service tiers cannot even be derived.
Project and cost centreThe word "project" appears zero times in the store, the app and all five migrations. A mission carries only location TEXT. For a geotechnical firm, the primary reporting axis was never modelled.
A real audit trailThe table is correctly append-only and receives nothing. There is also no decided_by, so who approved a request is not recorded at all.
Reporting and exportNo CSV, Excel, PDF or print view — grep for all of them returns zero. recharts is a declared dependency that is never imported.
Notification deliveryNotifications exist only as in-app rows. Nobody is told anything unless they log in and look, which for an approval queue means requests sit unnoticed.
Password resetNo flow exists, and none could work against the non-routable @hr.company.internal domain. Every lockout is a manual database intervention.
Conflict awarenessvalidateMissionFields receives no existing-request list, so an employee can hold approved annual leave and an approved site mission on the same day. Payroll would pay both.
A rejection loopRejection is a dead end: no resubmit, no amend, no duplicate, and no withdraw path anywhere. The highest-volume real-world loop does not exist.
Data protection postureNo region pinning on the Supabase client, health data collected in a free-text reason box, and zero hits for consent, retention, DPO or PDPL.

What is genuinely well done

The audit should be fair: the intent visible in this codebase is consistently better than the result, and several things here are subtleties that experienced teams get wrong.

  • The approver is derived from employee.manager_id and the employee cannot choose it. ApproverInfo is read-only. This is the single most important rule in the domain and it is right.
  • managerId, managerName and leaveTypeName are snapshotted onto the request at creation, so a later reorg does not rewrite history. Correct historical-approver instinct.
  • A surrogate UUID primary key with a separate employee_number business key is the right modelling call.
  • is_hr() as SECURITY DEFINER with SET search_path = public correctly breaks the RLS recursion that traps most teams.
  • ON DELETE RESTRICT on the request foreign keys properly refuses to orphan absence history.
  • The Phase 1.1 self-review found a genuine tautology bug in its own earlier policy and fixed it. That is real engineering discipline.
  • Approve and reject are guarded on both status and manager ownership, and the manager request-detail page has the ownership redirect the employee page is missing.
  • The design system is coherent and complete — nineteen screens with consistent states, and no "coming soon" placeholders anywhere.

08

Roadmap

Three horizons. Do not start Horizon 2 before Horizon 1 is finished — every item below depends on the layer above it.

Horizon 1 — Make it truthful
Stop the product from claiming things that are not true. Roughly four to six weeks.
  1. Make it runnable. Add index.html and a real entry point, drop the library build, add dev, typecheck, lint and test scripts. Fix the TS2440 duplicate and the three corrupted icon imports.
  2. Pick one identity key. Use the profiles UUID end to end, or employeeNumber end to end. Not both. This single change unblocks requests, My Team, notifications and every HR join.
  3. Provision auth users. Write the migration or edge function that creates auth.users rows whose ids match the seeded profiles, and implement createHRUserCredential server-side so HR-created employees can actually log in.
  4. Move the data layer to Postgres. Replace store.ts's sessionStorage with real queries. Four of five tables are currently dead.
  5. Fix the RLS layer. Verify the is_hr() EXECUTE grant against a live database. Constrain requests_insert on manager_id and status. Write the notification and audit triggers Phase 1.1 promised. Lock requests_update to the three columns its own header claims. Add decided_by and updated_at.
  6. Close the security holes. Add the ownership guard to EmployeeRequestDetailPage, purge the store on logout, delete src_extracted/ and src.zip, and rotate all eight credentials.
  7. Wire session restore. Call subscribeToAuthChanges and give ProtectedRoute a pending state so refresh does not flash-redirect to login.
  8. Fix what HR sees. The "Invalid Date" bug, the missing Try Again button, and the mobile calendar overflow.
Horizon 2 — Make it an HR system
Add the domain model that currently does not exist. Roughly three to four months.
  1. Entitlement and balance engine. Leave types carry rules; employees carry balances; requests carry a computed day count. Without this the system cannot answer "how many days do I have left" or hand anything to payroll.
  2. Working calendar. Egyptian public holidays, a Friday–Saturday weekend, half-days. Leave duration is meaningless until this exists.
  3. Employment lifecycle. Hire date, contract type, probation, termination and rehire — the prerequisite for Labour Law 12/2003 service tiers.
  4. Effective-dated history. Stop overwriting profiles. Every day without this destroys reporting history permanently, so it is more urgent than its position suggests.
  5. Cancellation, withdrawal and amendment. Including the resubmit loop after a rejection.
  6. Delegation and escalation. An out-of-office deputy, an HR override, and an SLA on pending approvals.
  7. Attachments and comment threads. Medical certificates, and a real authored comment history rather than one overwritten nullable column.
  8. Project and cost-centre dimension. Missions attach to a project code, not a free-text location string. This is the axis GEOTECH's own executives will ask for first.
  9. Arabic and RTL. A real Arabic face, dir switching, and a Sunday-first calendar.
  10. Working audit trail and a data-protection posture. Region pinning, retention schedule, consent record, subject-access path.
Horizon 3 — Make it excellent
The things that make people prefer it to a WhatsApp message.
  1. Analytics. Absence rate by department and project, approval turnaround by manager, leave liability for Finance, concurrent-absence risk on a project team.
  2. Export everywhere. CSV, Excel and PDF from every table. HR staff need this daily.
  3. Email and push delivery, so approvals do not sit unseen.
  4. Manager bulk actions and a team coverage view — the input that actually governs a leave decision.
  5. Payroll and time-and-attendance hand-off.
  6. MFA, SSO and self-service password reset on a routable email domain.
  7. A real mobile experience for surveyors filing mission requests from site.
